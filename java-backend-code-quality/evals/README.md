# 语义评测

`semantic-cases.json` 保存 Java 后端质量规则的代表性决策场景。它用于检查 Agent 是否做出了正确判断，不要求固定措辞，也不替代真实项目中的源码、契约和测试。

每个用例包含：

- `fixture`：提供给 Agent 的最小代码或任务背景
- `expected_decisions`：回答中必须体现的判断
- `disallowed_decisions`：不能出现的错误判断
- `triggers`：该场景应加载的详细规则
- `mode`：`planning`、`analysis`、`implementation` 或 `review`，分别对应规划、分析、实现和审查

建议使用没有继承原讨论结论的新会话或独立评测者，将 Skill、单个 fixture 和对应模式的真实用户提示交给它，不提供预期答案。评测者按含义判断是否覆盖所有期望决策，而不是比较原句。编码循环场景应特别记录任务是简单还是复杂、何时触发阶段检查、何时因新边界升级，以及是否在语义不确定时暂停。发现失败后先修正规则，再重新运行全部受影响用例。

任务模式场景检查未改动代码能否进入指定分析范围、规划是否先核对契约、解释是否越界成为重构，以及可选设计是否被误报。记录实际读取的引用、改动行为和验证命令；只读任务不得修改源码或初始化提示文件，也不能把计划测试、旧版本测试或结构校验当成新方案已经验证。模式切换后保留用户已确认的要求、范围和决定；不为执行既有授权重复审批。

注释文案场景要求评测者给出具体改写或保留理由，再逐项检查：是否说清对象和动作、是否保留原有条件和保证、是否编造原因，以及必需的 JavaDoc、校验簇和 catch 说明是否仍在。行为变化时，检查整条注释能否独立表达当前规则，以及方法和阶段说明是否同步；已有注释只提供格式参考与待核实线索，不能把旧句加例外当成默认更新方式。准确且未受影响的说明应保留。领域术语和真实因果句可以保留，不按固定句式或词语黑名单评分。记录改写原文及判断依据，不把“建议文案更自然”当作已经完成文案验证。

资料校准场景覆盖方法职责、日期区间与开关包装、快照读取时点、状态名称、独立常量与结构数字、循环与 Stream、借用和自有资源、关闭异常、超时结果不确定及多层重试。记录具体保留或调整方案及行为依据；不因答案提到了书名或设计术语就判通过。阶段检查仍要执行，但不要求每个清楚的调用都新增正文注释。

整体流程场景同时检查代码结构、诊断覆盖和证据边界：既要识别只为摘要服务的状态变量和包装，也要保留真实审计、资源关闭和有用的异常转换。记录每种相关失败如何关联请求、响应和调用方，并区分测试已执行内容与 Mock 后未覆盖的行为。项目提示场景区分稳定规则入口和单次方案；排障场景区分存在的缺陷与本次故障的已证实根因。不能只逐条匹配规则，而忽略组合后是否更难理解。

业务日志场景记录具体字段、取值时点、操作关联方式和结果含义，检查可变对象的前后快照、事务失败、已有日志复用及无需补日志的简单场景。命名场景要求给出实际名称和理由，检查常见词是否保持原职责、项目术语和外部签名；不能仅因为换成了短词就通过。

跨阶段场景使用通用 Java 服务、集合、配置、序列化和异常背景，检查最终赋值、缺失结构、身份与数量关系、可比单位、不同目的的判定、版本与表示边界，以及职责迁移前后的调用和失败行为。方法与诊断场景同时检查隐藏输出、必要快照、采集责任和正常流程可读性。记录具体输入、最终结果、反例及判断依据；既有缺陷、假设或需求调整不能自动成为新的修复范围。相同业务名或内部字段不是通过依据，普通局部映射也不应加载全部引用。

下面的命令只校验评测文件结构，不运行模型，也不能证明语义行为正确：

```powershell
py -3 scripts/validate_semantic_evals.py evals/semantic-cases.json
```
